Python · 実測レポート

Python の下にある C/C++

HEIC を JPEG に変換するツールを Python で書いた。速かった。 では、その速さはどこから来たのか——実際に数えてみた記録。

私が書いた Python 60.2 KB 1,173 行(エンジン 431 / GUI 574 / CLI 168)
その下のネイティブコード 56.0 MB 21 個のコンパイル済みバイナリ(C / C++)
比 約 950 倍 重い処理はすべて下の層で起きている

図1：写真 1 枚が変換されるまでの断面

img.save() という 1 行が、Python とネイティブコードの境界をまたぐ。 帯の厚みは、その層が担っている実際の重さにおおよそ対応させてある。

図2：ツール自体の構成

GUI とコマンドラインで同じ変換処理を二重に書かないよう、エンジンを 1 つに寄せてある。 並列化するときに出力先の名前を取り合う問題があり、そこだけ排他制御を挟んでいる。

どの要件が、どの層を要求するか

「C++ でないと駄目」なのは、言語の速さではなく満たすべき制約で決まる。 逆に言えば、この表のどれにも当てはまらない仕事に C++ を選ぶ理由は薄い。

制約ごとに必要となる実装層の対応表
制約具体例必要な層
締め切りが絶対 音声処理(数 ms でバッファを埋める)、ゲームの 1 フレーム、車載制御 ネイティブ
実行環境が極小 ファームウェア、RAM が KB 単位の組み込み機器 ネイティブ
規模で効いてくる データセンターの CPU 数 %、モバイルの電池 ネイティブ
他言語から呼ばれる Python / C# / Java / Go すべてから使われるライブラリ ネイティブ
土台そのもの OS、ブラウザ、DB、ffmpeg、そして Python 処理系自身 ネイティブ
上のどれでもない 業務ツール、写真処理、自動化、Web、データ分析 Python でよい

補足

ネイティブ層の新規開発では、いま Rust が C++ の領域に入ってきている。 Linux カーネル、Android、Windows、Chrome が新しい部分を Rust で書き始めた。 C++ が今も巨大なのは技術的優位というより、40 年分の既存資産がそこにあるからで、 ゲームエンジン・CAD・DAW・金融インフラは今後も C++ のまま動き続ける。

逆説的なのは AI で、PyTorch を触るのは Python でも、GPU を回しているのは CUDA C++ である。 ローカル LLM の定番は名前からして llama.cpp だ。 Python の需要が増えた分、その下を支える C++ の需要も増えた。

境界がどこにあるかを知っておく

C++ を書けるようになる必要はない。ただ、自分のコードのどこから下が C/C++ なのかが 見えていると、性能が出ないときに切り分けができる。

「Python が遅い」のか、「Python のループで画素を 1 つずつ回してしまっている」のか。 だいたいは後者で、境界より上に処理を書いてしまったことが原因になる。 今回のツールが速かったのは、重い処理をすべて境界の下へ渡せていたからにすぎない。

数値はすべて実環境で計測。ネイティブバイナリのサイズは .venv/Lib/site-packages 配下の .pyd / .dll 21 ファイルの合計。変換時間は実写 HEIC 3 枚による実測値。
