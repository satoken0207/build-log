見張り番

ONVIF対応の防犯カメラを、説明書なしで繋げるWindowsアプリ。 映像を見ながら、動きがあった場面を高画質のまま記録する。

市販の防犯カメラの多くはONVIFという共通規格に対応している。にもかかわらず、 パソコンのソフトから繋ごうとすると高い確率で詰まる。IPアドレスの調べ方、 ポート番号、ONVIF用アカウントの作り方がメーカーごとに違い、 そもそもONVIFが初期状態でオフになっている機種もある。 「規格に対応している」ことと「繋がる」ことは別だった。

見張り番は、そこを一つずつ潰していくアプリ。 起動すると自動でネットワーク上のカメラを探し、映像を表示して、 動きがあったときだけ録画する。

繋がるまでを設計する

起動と同時にWS-Discoveryでカメラを探し、見つかったものをメーカー名と型番で一覧に出す。 利用者に何も押させないところから始める。IPアドレスで並べても、 自分のカメラがどれか分からないので出さない。

ONVIFの認証は、カメラとパソコンの時計が数秒ずれているだけで失敗する。 そのため認証の前に必ずカメラの時刻を取得して、その差を織り込んでから署名を作っている。 これを入れるまで、正しいパスワードでも繋がらない個体があった。

繋がらなかったときは「接続エラー」で終わらせず、原因の候補と次にやることを日本語で出す。 ONVIFがオフ、専用アカウントが未作成、別のセグメントにいる、といった詰まり方ごとに文面を変える。 メーカー固有の案内は外部ファイルで持たせていて、現在の登録は TP-Link(Tapo / VIGI)と、機種を特定できなかった場合の汎用案内の2件。 実機で確かめた事実だけを足していく方針にしている。

ONVIFが使えないカメラのための逃げ道

実際に手元の2台目がONVIFを喋らなかった。RTSPだけは生きていたので、 そこから映像を取れる導線を用意した。

ただし「RTSPのURLを入力してください」とは聞かない。一般の購入者はURLの形を知らないし、 機種ごとに違い、調べる手段も持たない。聞くのはIPアドレスとIDとパスワードだけにして、 メーカー各社で使われている28種類のURL形式をこちらが順に試す。 当たれば画質の選択肢として提示する。手元の環境では2.4秒ほどで判定が終わる。

実機に当てて分かったこと

単体テストが全部通っていても、実機に繋ぐと前提が崩れる。 この製品で作業時間の大半を持っていったのは、その差分だった。

401は「パスワードが違う」とは限らない。 あるカメラは、知らないURLに対しても404ではなく401を返してきた。 1回の401で打ち切る作りにしていたため、経路が存在しないだけなのに 「パスワードが違います」と誤って案内していた。 かといって無制限に試すとアカウントがロックされる。今は一度も成功していない場合に限り、 数回の猶予を置いてから諦めるようにしている。

H.264に変更できないカメラが実在する。 見張り番はH.264のみに対応している。H.265のカメラには 「設定で圧縮方式をH.264に変えてください」と案内していたが、 2台目の実機はそれができなかった。カメラの独自プロトコルで設定を読み書きして確かめたところ、 対応する方式がH.265の1つしか無く、H.264を要求しても拒否された。 設定画面にコーデックの項目自体が存在しない。 そのため案内文に「変更する項目が見つからない場合は、そのカメラは H.265専用のため利用できません」という一文を足した。 存在しない設定を探させ続けるのは、映らないことより不親切だと判断した。

接続が切れても例外が出ないことがある。 自動再接続は「切れたら例外が出る」ことを前提にしている。 ところが相手が黙り込むだけの切れ方をすると、読み取りは永久に待ち続け、例外が出ない。 例外が出ないので再接続も起きず、画面は「監視中」のまま録画だけが止まる。 無人で動かす製品では、これは「起動しない」より悪い壊れ方になる。 今は10秒無音で打ち切って繋ぎ直すようにしていて、 実機の手前に中継を挟んで通信だけを止める試験で確認している。

空白やワープを「隠さず、増やさず」直す

録画の空白や時間の飛びを調べると、単にフレームを詰めればよいわけではなかった。 カメラの時計が突然飛ぶ場合と、本当に通信が途切れた場合は、見た目が似ていても意味が違う。 本物の欠落まで滑らかに見せると、防犯映像として残すべき事実を消してしまう。

そこで通常はカメラのRTP時刻を使い、実測で確認した異常ジャンプだけを受信間隔へ置き換える。 パケット欠落や停止は欠落として残す。H.264の分割フレームが途中で欠けたときは、 壊れた映像を無理に組み立てず、次のIDRから復旧する。音声も同じ時間軸に揃えた。

補正前のRTP時刻と受信時刻は付随記録へ残す。 見た目を整えるだけでなく、あとから「なぜこの時刻になったか」を追える作りにしている。

録画の作り

動体検知で録画する。検知の2秒前から記録が始まるので、 人が画面に入ってくるところから残る。動きが止まって5秒で区切り、 長く続く場合も5分で分割する。

誤検知を減らすために、画面の一部を検知対象から外せる。 道路や木、点滅する表示など「動いても放置していい場所」を四角で囲って除外する。 監視する時間帯も曜日ごとに設定でき、時間外は録画せず映像だけ映す。 検知したときの音は内蔵のビープとサイレン、または手持ちのWAVから選べる。 音源ファイルは同梱せず、波形をその場で生成している。

高画質側は、カメラから届いたH.264を再圧縮せずに保存する。 実機では2560×1440、249コマ / 9.96秒 = 25.00fpsで、取りこぼし0を確認した。 ナンバーの細部も録画から読み取れるところまで改善している。 画質の選択肢は「軽く録る」「きれいに録る（パソコンの負担が大きくなります）」と、 効果と代償がその場で分かる言葉にした。

外部ランタイムを持たない

FFmpegもOpenCVも同梱していない。H.264の復号と符号化はWindowsに標準で入っている Media Foundationを直接呼んで行っている。COMのインターフェースを手で定義する必要があり、 仮想関数表の並びを間違えて何度か嵌ったが、 配布物にネイティブDLLが1つも増えないことと、 H.264のライセンスをOS側に寄せられることを優先した。

配布は.NET 10のセルフコンテインド単一実行ファイル。 利用者が.NETを入れる必要はなく、展開して起動するだけで動く。

  • ONVIF / WS-Discovery
  • RTSP / RTP over TCP
  • H.264
  • Media Foundation
  • WPF
  • DPAPI

今の状態

出荷前の検証中。隔離した環境で自動試験1,138件を実行し、1,115件が合格した。 残る23件はDPAPIやレジストリなど隔離環境では成立しないOS統合試験として分けて管理している。 自動再接続、無音になった接続の検出、日付をまたぐ録画、 2560×1440 / 25.00fpsの無加工保存は実機で確認済み。

一方で、実機で動作を確認できているカメラはまだ1機種だけ(TP-Link C520WS)。 2台目はH.265専用機だったため、動作確認ではなく 「対応できないカメラの実例」として設計に反映される結果になった。 URL形式の一覧には他社の書き方も入れてあるが、そちらは未検証。 対応機種を広く見せるより、確かめた範囲を正直に出すことを優先している。

国内のソフト配布サイトVectorでの公開を予定していて、 使用許諾や試用期間まわりの実装は済んでいる。 出荷判定は課題一覧と167項目の受入テストで管理していて、 「ビルドが通ることとテストが通ることは、機能が呼ばれていることを保証しない」 という反省から作った文書になっている。 実際、実装もテストも完成しているのにアプリから一度も呼ばれていない機能が まとめて見つかったことがあった。24時間の正規soakと人の目・耳で行う受入を終えてから配布する。
